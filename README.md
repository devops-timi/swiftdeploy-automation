# SwiftDeploy

A declarative deployment tool that generates its own infrastructure. You write one YAML file — SwiftDeploy handles everything else.

---

## What Is SwiftDeploy?

SwiftDeploy is a CLI tool that manages the full lifecycle of a containerised service. Instead of manually writing Nginx configs and Docker Compose files, you describe what you want in `manifest.yaml` and SwiftDeploy generates all configuration, starts your stack, enforces deployment policies, and gives you a live dashboard — all from a single executable script.

**The core principle:** `manifest.yaml` is the only file you ever edit manually. Everything else is derived from it.

## Project Structure

```
swiftdeploy-automation/
├── manifest.yaml                    ← The only file you edit
├── swiftdeploy                      ← The CLI tool

│   └── docker-compose.yml.tmpl      ← Docker Compose template
├── policies/
│   ├── infrastructure.rego          ← Deployment safety policy
│   ├── canary.rego                  ← Canary promotion policy
│   └── data.json                    ← Policy thresholds
└── README.md
```

**Generated files (do not edit manually):**
```
nginx.conf          ← Generated by: ./swiftdeploy init
docker-compose.yml  ← Generated by: ./swiftdeploy init
history.jsonl       ← Written by: ./swiftdeploy status / deploy / promote
audit_report.md     ← Generated by: ./swiftdeploy audit
```

## The Manifest

`manifest.yaml` is the single source of truth. All generated configs are derived from it.

```yaml
services:
  image: swift-deploy-1-node:latest   # Docker image for your app
  port: 3000                          # Port the app listens on inside the container
  mode: stable                        # Deployment mode: "stable" or "canary"
  version: "1.0.0"                    # App version string
  restart: unless-stopped             # Docker restart policy

nginx:
  image: nginx:latest                 # Nginx Docker image
  port: 8080                          # Port exposed to the outside world
  proxy_timeout: 30                   # Nginx upstream timeout in seconds

opa:
  image: openpolicyagent/opa:latest   # OPA policy engine image

network:
  name: swiftdeploy-net               # Internal Docker network name
  driver_type: bridge                 # Network driver

contact: "admin@swiftdeploy.local"    # Contact shown in JSON error responses
```

## CLI Reference

### `./swiftdeploy init`

Reads `manifest.yaml` and generates `nginx.conf` and `docker-compose.yml` from templates. Run this whenever you change the manifest.

```bash
./swiftdeploy init
```

```
── swiftdeploy init ──────────────────────────────────
  ✓ Generated nginx.conf and docker-compose.yml successfully.
── init complete ─────────────────────────────────────
```

---

### `./swiftdeploy validate`

Runs 5 pre-flight checks before deployment. Exits with a non-zero code if any check fails.

```bash
./swiftdeploy validate
```

```
── swiftdeploy validate ──────────────────────────────
[1/5] Checking manifest.yaml exists and is valid YAML...
  ✅ PASS: manifest.yaml is valid YAML
[2/5] Checking required fields...
  ✅ PASS: All required fields present
[3/5] Checking Docker image exists locally...
  ✅ PASS: Image 'swift-deploy-1-node:latest' found locally
[4/5] Checking Nginx port availability...
  ✅ PASS: Port 8080 is free on the host
[5/5] Validating generated nginx.conf syntax...
  ✅ PASS: nginx.conf is syntactically valid
── validation complete: ALL CHECKS PASSED ────────────
```

**What each check does:**

| Check | What it verifies |
|-------|-----------------|
| 1 | `manifest.yaml` exists and is parseable YAML |
| 2 | All required fields are present and non-empty |
| 3 | The Docker image referenced in the manifest exists locally |
| 4 | The Nginx port is not already bound on the host |
| 5 | The generated `nginx.conf` passes `nginx -t` syntax validation |

### `./swiftdeploy deploy`

Generates configs, validates, starts the full stack, waits for health checks to pass, then runs the OPA infrastructure policy check.

```bash
./swiftdeploy deploy
```

```

 ✔ Container swiftdeploy-app-1    Healthy
 ✔ Container swiftdeploy-opa-1    Started
 ✔ Container swiftdeploy-nginx-1  Started
Polling health endpoint http://localhost:8080/healthz (up to 60 seconds)...
```

### `./swiftdeploy promote [stable|canary]`

Switches the deployment mode. Before switching, it samples metrics over a 30-second window and asks OPA if promotion is safe. Only the app container is restarted — Nginx stays up.

```bash
./swiftdeploy promote canary
./swiftdeploy promote stable
```

**Healthy promotion (approved):**
```

── OPA Pre-Promote Policy Check ──────────────────────

  Last 30s: 12 requests, 0 errors
  Error rate: 0.0000%, P99 latency: 5.00ms
  ✅ PASS: Canary policy approved promotion
  ✓ Updated manifest.yaml to canary
  Recreating app container only...
  ✅ PASS: Promotion to canary active and verified.
```

**Blocked promotion (policy violation):**
```
── OPA Pre-Promote Policy Check ──────────────────────

    ↳ P99 latency 10000ms exceeds maximum 500ms over last 30s
❌ Promotion blocked by policy.
```

### `./swiftdeploy audit`

Reads `history.jsonl` and generates `audit_report.md` — a GitHub Flavored Markdown report with a full timeline, policy violations, and mode changes.

```bash
./swiftdeploy audit
cat audit_report.md
```

---

### `./swiftdeploy teardown [--clean]`

Stops and removes all containers, networks, and volumes.

```bash
./swiftdeploy teardown           # Stop everything
./swiftdeploy teardown --clean   # Stop everything + delete generated configs
```

## API Endpoints

All traffic goes through Nginx on port 8080. The app port (3000) is never exposed directly.

### `GET /`

Returns a welcome message with the current mode, version, and timestamp.

```bash
curl http://localhost:8080/
```

```json
{
  "message": "Welcome to SwiftDeploy! Running in canary mode.",
  "mode": "canary",
  "version": "1.0.0",
  "time": "2026-05-05T21:00:00.000000+00:00"
}
```

### `GET /healthz`

Liveness check. Returns status and process uptime in seconds. Never affected by chaos.

```bash
curl http://localhost:8080/healthz
```

```json
{
  "status": "ok",
  "uptime": 342.15
}
```

### `GET /metrics`

Prometheus-format metrics. Scraped by `swiftdeploy status` and the pre-promote policy check.

```bash
curl http://localhost:8080/metrics
```

```
# HELP http_requests_total Total HTTP requests
# TYPE http_requests_total counter
http_requests_total{method="GET",path="/",status_code="200"} 142
# HELP app_uptime_seconds Seconds since app started
# TYPE app_uptime_seconds gauge
app_uptime_seconds 342.15
# HELP app_mode Current deployment mode (0=stable, 1=canary)
# TYPE app_mode gauge
app_mode 1
# HELP chaos_active Current chaos state (0=none, 1=slow, 2=error)
# TYPE chaos_active gauge
chaos_active 0
```

### `POST /chaos` *(canary mode only)*

Simulates degraded behaviour. Returns 403 in stable mode.

```bash
# Slow mode — sleep N seconds before every response
curl -X POST http://localhost:8080/chaos \
  -H "Content-Type: application/json" \
  -d '{"mode": "slow", "duration": 5}'

# Error mode — return 500 on ~50% of requests
curl -X POST http://localhost:8080/chaos \
  -H "Content-Type: application/json" \
  -d '{"mode": "error", "rate": 0.5}'

# Recover — cancel all chaos
curl -X POST http://localhost:8080/chaos \
  -H "Content-Type: application/json" \
  -d '{"mode": "recover"}'
```

## OPA Policy Engine

SwiftDeploy uses [Open Policy Agent](https://www.openpolicyagent.org/) to make all allow/deny decisions. The CLI never decides — it only sends data and surfaces OPA's reasoning.

### Infrastructure Policy (`policies/infrastructure.rego`)

Evaluated before every `deploy`. Blocks deployment if host resources are insufficient.

| Check | Threshold |
|-------|-----------|
| Disk free | ≥ 10GB |
| CPU load average | ≤ 2.0 |
| Memory usage | ≤ 90% |

### Canary Safety Policy (`policies/canary.rego`)

Evaluated before every `promote`. Samples metrics over 30 seconds and blocks promotion if the service is unhealthy.

| Check | Threshold |
|-------|-----------|
| Error rate (last 30s) | ≤ 1% |
| P99 latency (last 30s) | ≤ 500ms |

### Adjusting Thresholds

All thresholds live in `policies/data.json`. Edit this file to adjust limits without touching the policy logic:

```json
{
  "infrastructure": {
    "min_disk_free_gb": 10,
    "max_cpu_load": 2.0,
    "max_mem_percent": 90
  },
  "canary": {
    "max_error_rate_percent": 1.0,
    "max_p99_latency_ms": 500
  }
}
```

After editing `data.json`, restart OPA to reload:

```bash
docker compose restart opa
```

## Testing the Policy Gates

### Test the infrastructure gate (disk)

```bash
# Fill disk temporarily (adjust size to exceed your threshold)
fallocate -l 5G /tmp/diskfill

# Try to deploy — should be blocked
./swiftdeploy teardown --clean
./swiftdeploy deploy

# Clean up
rm /tmp/diskfill
```

### Test the canary gate (error rate)

```bash
./swiftdeploy deploy
./swiftdeploy promote canary

# Activate 50% error chaos
curl -X POST http://localhost:8080/chaos \
  -H "Content-Type: application/json" \
  -d '{"mode": "error", "rate": 0.5}'

# Generate traffic
for i in {1..100}; do curl -s -o /dev/null http://localhost:8080/; sleep 0.3; done &

# Try to promote — OPA will block it
./swiftdeploy promote stable

# Recover
curl -X POST http://localhost:8080/chaos \
  -H "Content-Type: application/json" \
  -d '{"mode": "recover"}'
```

## Full Workflow Walkthrough

```bash
# 1. Build image
docker build -t swift-deploy-1-node:latest .

# 2. Deploy the stack
./swiftdeploy deploy

# 3. Check it's working
curl http://localhost:8080/
curl http://localhost:8080/healthz

# 4. Watch the live dashboard
./swiftdeploy status

# 5. Promote to canary
./swiftdeploy promote canary

# 6. Test chaos in canary mode
curl -X POST http://localhost:8080/chaos \
  -H "Content-Type: application/json" \
  -d '{"mode": "error", "rate": 0.5}'

# 7. Watch policy fail in status dashboard
./swiftdeploy status

# 8. Recover and promote back to stable
curl -X POST http://localhost:8080/chaos \
  -H "Content-Type: application/json" \
  -d '{"mode": "recover"}'
./swiftdeploy promote stable

# 9. Generate audit report
./swiftdeploy audit
cat audit_report.md

# 10. Tear down
./swiftdeploy teardown --clean
```

## Security Notes

- The app container runs as `appuser` (non-root) with all Linux capabilities dropped
- Nginx drops `NET_ADMIN`, `SYS_ADMIN`, and `SYS_PTRACE` capabilities
- The app port (3000) is never exposed to the host — all traffic routes through Nginx
- OPA is not accessible through Nginx — it communicates only with the CLI
- All container images are under 300MB
- Nginx config and Docker Compose files are mounted read-only where possible
